# 多代理审查-修改工作流

核心原则：主代理只做检查、分派、汇总、融合与验证决策，不亲自做大段执行。检查、修改、验证分别交给独立的子代理，避免“自己改、自己验收”。

## 何时使用

- 一次改动跨多个文件或模块，需要先摸清风险再动手
- 用户要求“系统审查”“全面检查”“迁移 / 重构”，且审查结果大概率要落地修改
- 改动的正确性不能由执行者自证，需要独立验收

## 何时不用

- 单文件、单函数的小修小补：直接改更快，开子代理只会增加开销
- 纯问答、纯解释性任务
- 用户只要一份分析报告、明确不改代码：只跑第一层，然后直接汇总

## 环境适配（执行前必读）

流程本身与具体工具无关。启动前先确认当前环境具备哪些能力，按下表映射；表中给出的是 CodeBuddy 的落地方式，换到其他 agent 平台时用等价能力替换。

| 角色 | 能力要求 | CodeBuddy 落地 |
|---|---|---|
| 只读检查代理 | 只读文件与搜索，不能写 | `Task` + `code-explorer`（只读子代理） |
| 需续跑的代理 | 保留上下文，可追加任务 | `Task` 传 `name` 起团队成员，再用 `send_message` 追加检查范围 |
| 可写执行代理 | 能编辑文件 | 环境无此类子代理时，由主代理成批执行（见第二层） |
| 独立验证代理 | 只读，且与修改者不是同一实例 | 新起一轮 `Task` + `code-explorer`，不复用修改过程上下文 |
| 进度跟踪 | 每层可追踪 | `todo_write` |

环境缺少可写子代理时不要硬凑：主代理自己按批次改，但验证环节仍必须由独立只读代理执行。

## 第零层：执行前确认（默认强制执行）

启动任何子代理之前，先向用户展示下列内容并等待确认。用户在任务中明确说了“直接做”“不用确认”等，可跳过本层。

展示只列要点，不复述本流程全文：

1. **任务理解**：用自己的话复述目标，列出尚不确定、需要用户澄清的点
2. **分配计划**：第一层检查代理的检查范围与审查标准；预判哪些问题可能走 simple / batch / complex 分流
3. **验收标准**：判定“完成且正确”的具体标准

任务理解中存在不确定处时先提问，不要自行假设。用户确认后才进入第一层。

## 第一层：只读检查（风险前置分级）

启动只读子代理，工具范围严格限制为读取与搜索。在 prompt 中要求输出结构化问题清单，每条包含：

| 字段 | 要求 |
|---|---|
| ID | 唯一编号，如 C1、C2 |
| 问题描述 | 一句话说明 |
| 严重程度 | critical / warning / info |
| 风险等级 | simple（单文件、≤5 行、逻辑明确）/ batch（多文件但模式统一）/ complex（需重新设计实现、涉及架构判断） |
| 位置 | 文件:行号 |
| 建议方向 | 修复思路，不要求完整代码 |

风险等级由检查代理在检查时直接标注，把第二层的分流判断前置。

拿到反馈后，判断哪些修、哪些忽略、哪些需要进一步深挖。深挖时复用同一个检查代理追加范围，不重新 spawn。

## 第二层：修改分流（按风险等级分派）

| 风险等级 | 执行者 | 操作要点 |
|---|---|---|
| simple | 复用原检查代理（若其具备写权限）；否则由主代理集中成一批改完 | 复用前必须在 prompt 中明确切换模式：“现在进入修复模式，只修改已确认的 simple 问题，complex 问题只报告不修改” |
| batch | 新的执行者，以原检查报告为输入 | 只传问题清单（ID + 位置 + 建议方向），不传检查代理的完整对话历史 |
| complex | 新的执行者，给更完整的上下文 | 不传原检查代理上下文，只传问题描述与涉及文件路径 |

分流规则：

- 检查代理默认只读，simple 修改走轻量路径
- 检查代理一开始就配了写权限时，simple 直接续跑复用，最省 token
- 同一批 simple 问题合并给一个执行者，不要一条问题开一个代理
- complex 问题必须先出实现方案，经用户或主代理确认后再动手
- 同一批次的修改不要跨文件乱跳，按文件/模块分组，改完一批立刻看 diff 自检

## 第三层：独立验证（不信任自我验证）

修改完成后，禁止让执行修改的一方自我验证。

启动独立的只读验证代理，只接收：

1. 原始问题清单（修改前，含 ID）
2. 修改后的 diff 或变更文件列表

要求逐条输出：

| 字段 | 要求 |
|---|---|
| 对应问题 ID | 如 C1 |
| 是否已解决 | yes / no / partial |
| 是否引入新问题 | yes / no，若有则描述并标位置 |
| 结论 | 该条通过 / 需返工 |

根据结果做最终融合：全部通过则汇总交付；有返工的，按返工问题的风险等级回到第二层重新分流，不要直接塞回原执行者。

## 交付格式

面向用户的最终汇总包含五块：

- 审查范围与所用判定标准
- 问题清单（ID / 严重程度 / 风险等级 / 位置 / 状态）
- 实际修改的批次与文件
- 验证结论（逐条通过情况、是否引入新问题）
- 遗留项与建议（未修的、需用户决策的）

## Vue 原生性判定标准（仅在 Vue 任务中适用）

非原生 Vue 用法，禁止交付：

- `document.querySelector` / `getElementById` 等直接查 DOM
- 手动 `addEventListener` / `removeEventListener` 绑定事件
- 直接操作 `innerHTML` / `textContent` 改写视图
- 滥用 `v-html` 渲染本可用模板表达的内容
- 用 `$refs` 直接修改 DOM 属性或结构（而非读取尺寸等必要信息）
- 手动操作 `classList` / `style` 代替 `:class` / `:style`

应使用的原生 Vue 实现：

- `ref` / `reactive` 管理状态
- `v-model` 双向绑定
- `@event` 模板事件绑定
- `computed` / `watch` 派生与响应
- 生命周期钩子处理副作用
- `:class` / `:style` 绑定样式

与 Vue 混合的 HTML/原生页面项目，先确认改动落在哪一层：HTML 侧的改动改 HTML，Vue 组件只在该组件确实是 Vue 实现时才动。

## 常见失误

- 跳过第零层直接开代理，用户不知道在查什么
- 把检查报告整段转给修改代理，浪费上下文并引入噪音，应只传 ID + 位置 + 建议方向
- 让修改代理自我验证，等于没验证
- 一条 simple 问题开一个子代理，开销大于收益
- complex 问题不先出方案就动手，返工成本最高
- 静态搜索的命中直接当缺陷上报，未核实就派活；先确认该命中是否真实生效

## 约束

- 检查代理默认只读；只有明确走“simple 复用”路径时才赋予写权限
- 复用检查代理做修改时，必须在 prompt 中显式声明模式切换
- 验证代理必须独立于修改执行者，且只读
- 主代理不亲自写大段代码；核心判断与融合由主代理做，执行交给子代理
- 分派任务时要求子代理“确保检查项都覆盖、确认无遗漏后再交付”，避免半成品回流
- 展示执行前确认时只列计划要点，不复述本流程全文
