# Super Agent · 多代理审查—修改工作流

> 一个**单文件、零依赖**的 Agent Skill：把主代理变成"超级调度者"——它自己不做大段执行，只负责检查分派、汇总融合与验收决策。
>
> 适配 **Claude Code**、**CodeBuddy**，以及任何支持子代理（subagent / Task 工具）的 Agent 工具。

> **尤其适合复杂任务。** 跨多个文件或模块、必须先摸清风险再动手、且"改得对不对"不能由改的人自己说了算的审查、迁移、重构——这类任务越复杂，本 Skill 的价值越明显：一台脑子扛不住的规模，拆给几个各司其职的子代理，再统一验收。
>
> 简单任务反而别用它，直接改更快（见[不适用场景](#不适用场景)）。

---

## 这是什么

平时让 Agent 干活，本质是**一个模型同时扮演"找问题的人、改代码的人、验收的人"**——它自己查、自己改、自己说改好了。

这个 Skill 把这件事拆开：主代理（super agent）只做**判断与调度**，检查、修改、验证分别交给不同的子代理，谁都不给自己打分。

你需要做的只有一件事：**像平时一样把任务说清楚**，剩下的分配、分流、验收由超级 Agent 决定。

```
你：帮我做整个系统的代码审查，找出漏洞。
Agent：好的，我先确认三件事——任务理解 / 分配计划 / 验收标准……
```

## 主对话只做四件事

用上这个 Skill 之后，主对话不再是一台"什么都要自己上的打杂机器"，而是一道关卡：

| 动作 | 主对话做什么 | 主对话不做什么 |
|---|---|---|
| **检查** | 确认任务理解、分配计划、验收标准，然后派活 | 不自己翻代码摸底 |
| **验收** | 收下子代理的交付，按验收标准逐条核对 | 不自证"应该没问题" |
| **打回** | 不合格就带着具体理由退回重做，循环到全部通过 | 不自己上手替它改 |
| **汇报** | 全部完成后给你一份汇总：改了什么、哪些验证通过、还剩什么 | 不把过程日志倒给你 |

整个循环是**自动的**：不合格就打回，打回再验，直到全部完成才来找你，不会中途把半成品丢给你判断。

**省下来的上下文，用来记住你的需求。** 读文件、翻实现、试错的细节都留在子代理自己的窗口里，主对话只保留问题清单、diff 结论和你的原话。窗口不被代码细节吃掉，长会话里它才记得住你早先定下的约定——命名规范、架构边界、必须兼容的接口、哪些目录不许碰。

## 它解决什么问题

| 痛点 | 后果 | 本 Skill 的做法 |
|---|---|---|
| 任务一跨文件就乱 | 边查边改，越改越歪，没人先摸风险 | 第零层先出计划、第一层先只读摸底，改动前就有分级清单 |
| 自我验收 | 改的人说"已修复"，等于没验收 | 第三层由**独立只读代理**逐条核对，与修改者不是同一实例 |
| 上下文污染 | 把整段检查对话塞给修改代理，噪音多、token 爆炸 | 只传 `ID + 位置 + 建议方向`，不传原始对话 |
| 主对话被编码细节占满 | 窗口越跑越满，长会话里慢慢忘掉你早先定的规矩 | 编码与试错留在子代理窗口，主对话只留判断、结论和你的需求 |
| 一条小问题开一个代理 | 开销大于收益 | 同类 simple 问题合并成一批 |
| 大改不先出方案 | 返工成本最高 | complex 问题必须先出方案、确认后再动手 |
| **子代理抢同一个文件** | 后写的覆盖先写的，**代码静默丢失** | 文件所有权串行化 + 按文件/模块分组（见下节） |

## 并发写冲突防护

多个子代理同时写同一个文件时，写入是"最后写赢"——先写的改动会被静默覆盖，而所有代理都以为自己是成功的。这是多代理协作里最难排查的一类 bug。

本 Skill 用以下机制把窗口压到最小：

1. **写入权集中**：同一时刻，一个文件只归属一个执行者。主代理不会把同一个文件同时派给两个子代理。
2. **按文件/模块分组分批**：同一批修改不跨文件乱跳，天然避免交叉覆盖。
3. **串行下发**：有依赖或可能重叠的批次按顺序执行，不并发启动写代理。
4. **验证代理只读**：验收环节永远不持有写权限，不会与执行者争抢文件。
5. **改完即看 diff**：每批结束立刻自检，让丢失在最小范围内被发现，而不是最后一次性爆炸。
6. **返工不塞回原执行者**：需要返工时按风险等级重新分流，避免同一代理带着旧上下文反复覆盖。

确实需要并行时，按**文件分区**并行（不同文件交给不同执行者），**同一文件严格串行**。

## 工作流程

```
用户一句话
   │
   ▼
[第零层] 执行前确认
   │   主代理复述目标 + 列出分配计划 + 定义验收标准  ── 等你确认
   ▼
[第一层] 只读检查（只给读与搜索权限）
   │   输出结构化问题清单：C1..Cn（严重程度 + 风险等级 + 位置 + 建议方向）
   ▼
[第二层] 按风险等级分流修改
   │   simple  → 轻量路径，同类问题合并成一批
   │   batch   → 新的执行者，只收问题清单
   │   complex → 先出实现方案，确认后再动手
   ▼
[第三层] 独立只读验证（不复用修改过程的上下文）
   │   逐条输出：是否已解决 / 是否引入新问题 / 通过 or 返工
   ▼
   ├── 全部通过 ──► 汇总交付
   └── 需返工   ──► 按风险等级回到第二层重新分流
```

**风险等级由检查代理现场标注**，把第二层的分流判断前置，省掉一次完整往返。

| 风险等级 | 判定标准 | 交给谁 |
|---|---|---|
| `simple` | 单文件、≤5 行、逻辑明确 | 复用原检查代理（若有写权限）；否则主代理集中成一批改 |
| `batch` | 多文件但模式统一 | 新执行者，输入=问题清单（ID + 位置 + 建议方向） |
| `complex` | 需要重新设计实现、涉及架构判断 | 新执行者 + 更完整上下文，**先方案后动手** |

## 安装

### Claude Code

```bash
git clone https://github.com/<your-name>/git-super-agent.git
mkdir -p ~/.claude/skills
cp -r git-super-agent/super-agent ~/.claude/skills/super-agent
```

Windows（PowerShell）：

```powershell
git clone https://github.com/<your-name>/git-super-agent.git
New-Item -ItemType Directory -Force "$env:USERPROFILE\.claude\skills" | Out-Null
Copy-Item -Recurse .\git-super-agent\super-agent "$env:USERPROFILE\.claude\skills\super-agent"
```

只给当前项目用时，放到项目内 `.claude/skills/super-agent/SKILL.md`。

### CodeBuddy

- **导入（推荐）**：`设置 → Skills → 导入 Skill`，选择 `super-agent` 目录。
- **项目级**：拷贝到工作区 `.codebuddy/skills/super-agent/SKILL.md`（随仓库共享）。
- **用户级**：放到用户配置目录的 `.codebuddy/skills/` 下（对所有项目生效）。

### 其他 Agent 工具

只要这个工具具备「子代理 / 任务分派」能力即可。把 `SKILL.md` 放进它约定的 skill、rules 或指令目录；没有 skill 机制的工具，直接把 `SKILL.md` 内容作为系统提示或规则文件挂上。文中给的是 CodeBuddy 的落地映射，其他工具用等价能力替换：

| 角色 | 能力要求 |
|---|---|
| 只读检查代理 | 可读文件与搜索，不可写 |
| 需续跑的代理 | 保留上下文，支持追加任务 |
| 可写执行代理 | 能编辑文件（环境没有时由主代理成批执行） |
| 独立验证代理 | 只读，且与修改者不是同一实例 |

## 使用

不需要记任何命令。Skill 的 `description` 会匹配意图自动加载，你正常说话就行：

| 你可以这样说 | 会发生什么 |
|---|---|
| 帮我做整个系统的代码审查，找出漏洞 | 三层流程全跑，交付逐条验证过的结论 |
| 把 auth 模块迁移到 TypeScript，改完要验证 | 先摸底 → 分批迁移 → 独立验收 |
| 全面检查这套 Vue 组件里的非原生写法并修掉 | 按 Vue 原生性标准判定 + 修复 + 复验 |
| 只要一份分析报告，别动代码 | 只跑第一层，直接汇总 |
| 直接做，不用确认 | 跳过第零层确认，立刻开工 |

## 不适用场景

- 单文件、单函数的小修小补：直接改更快，开子代理只会增加开销
- 纯问答、纯解释性任务
- 只需要一份分析报告且明确不改代码：只跑第一层即可

## 设计取舍

**为什么主代理不自己写代码？**
两个原因。一是"写"和"验收"必须是两拨人，否则等于自证；二是上下文预算——编码过程会吃掉大量窗口，把它外包出去，主对话才能把窗口留给判断和你的需求，而不是留给第 37 次失败的编译尝试。

**为什么只传问题清单，不传检查对话？**
检查代理的完整对话里有大量已经排除的猜测。把它们塞给修改代理，既浪费上下文，也会诱导它去"顺手改"未确认的地方。

**环境没有可写子代理怎么办？**
不硬凑。主代理按批次自己改，但**验证环节仍必须由独立只读代理执行**——这一条不妥协。

**为什么默认先确认再开工？**
任务理解偏差是多代理流程里最贵的错误：底层跑得再顺，方向错了全是白工。展示只列要点，不复述流程全文，确认成本很低。
